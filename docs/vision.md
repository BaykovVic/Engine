# Видение Sky Engine

Зафиксировано 2026-07-11 (после сравнительного анализа Unity и Unigine).

## Позиционирование

**Юзабилити Unity, инженерия Unigine.** Движок одинаково пригодный для
среднемасштабных симуляций и для игр. Не «клон Unity» и не «маленький
Unigine»: у каждого берётся то, в чём он лучший, и отбрасывается остальное.

## Принцип 1. Слой пользователя — язык Unity, без самодеятельности

Всё, что видит и трогает пользователь, следует конвенциям Unity — они
выучены индустрией, и наша аудитория (студенты, инди, инженеры) приходит
с ними:

- GameObject / Component / Inspector / Hierarchy / Project / Play-in-editor;
- префабы (SKYP), пакетный менеджер, C#-скрипты с `ScriptComponent`-жизненным
  циклом и сериализуемыми полями;
- Create → …, drag-and-drop, undo везде.

Из Unigine юзабилити **не берём ничего** — их редактор инженерный, не
дружелюбный. Проверка любого UX-решения: «как бы это назвал и где бы это
искал человек, пришедший из Unity?»

## Принцип 2. Рантайм-ядро — инженерия Unigine

Под капотом ориентир — модель Unigine, а не Unity:

- **Модель кадра (B17)**: физика с фиксированным шагом асинхронно,
  параллельно рендеру (однокадровый лаг — осознанный компромисс);
  update систем — по ядрам; наши push/pull sync-контракты готовы к этому.
- **Camera-relative rendering**: GPU считает во float относительно камеры —
  без джиттера вдали от начала координат. Полный double — только если
  появится реальный заказ на большие миры (за контрактом `core::math`).
- **Async-стриминг**: загрузка ассетов вне кадра, на `IJobScheduler`.
- **Headless — first-class**: `sky_player --headless` уже существует и
  остаётся полноправным режимом (CI, батч-прогоны симуляций), не побочным.
- **Данные как ассеты (B16)**: аналог Properties/ScriptableObject с
  наследованием (базовый ассет + переопределения).

## Принцип 3. Симуляции — first-class сценарий, не довесок

«Среднемасштабная симуляция» (сотни–тысячи агентов, воспроизводимые
прогоны) добавляет к дорожной карте требования, которых у чисто игрового
движка нет:

1. **Детерминизм**: фиксированный шаг физики (есть), стабильный порядок
   систем в планировщике, единый сеемый ГПСЧ для генерации. Один и тот же
   сценарий + сид ⇒ бит-в-бит одинаковый прогон. Тест на это — обязателен.
2. **Управление временем**: pause/step уже есть в Play; добавить time scale
   и покадровый прогон из API (не только из редактора).
3. **Сценарии как данные**: конфиг прогона — data-ассет (B16), не код.
4. **Метрики наружу**: `IDiagnostics` (счётчики/тайминги есть в core)
   получает экспорт в файл за прогон — симуляции живут отчётами.
5. **Масштаб**: тысячи агентов упираются в наш ECS-на-hash-map и
   однопоточность — B17 + data-oriented хранилище ECS поднимаются
   в приоритете (это уже не «перф-полировка», а входной билет).

Игровой трек при этом не страдает: Тир 1 (аудио, игровой UI, анимация,
экспорт билда) остаётся обязательным — симуляциям тоже нужны звук, HUD
и дистрибутив.

## Что это меняет в порядке работ

Порядок в `docs/backlog.md` пересобран под двойной трек:

1. **B8 GUID ассетов** — фундамент ссылок (нужен обоим трекам).
2. **B16 Data-ассеты** — конфиги симуляций и игровые данные.
3. **B17 Модель кадра** (async-физика + camera-relative + async-загрузка)
   — двигает оба трека, реализует часть B12.
4. **Детерминизм-пакет** — порядок систем, сеемый ГПСЧ, тест
   воспроизводимости, time scale API.
5. **B1 Аудио → B3 UI → B4 Билд** — игровой трек.
6. **ECS data-oriented хранилище** — когда появится первый сценарий на
   тысячи агентов (не раньше: преждевременно).

## Чего мы сознательно НЕ делаем

- Не гонимся за фотореализмом Unigine (SVT-терраины на 10 000 км, геоид,
  x20-оптика) — не наш масштаб.
- Не копируем юзабилити Unigine и трёхъязычие API.
- Не тащим двойную точность превентивно.
- Не строим «универсальный движок для всего» — два названных трека, и всё.
