# Sky Engine · Неделя 1 — фичи для студенческой команды

Это разбивка первой недели [8-недельного плана](plan-8-weeks-team.md) под
учебную команду: не пять строк на инженера, а самостоятельные тикеты с
чёткими критериями приёмки. Каждый тикет можно взять, сделать и сдать, не
дожидаясь соседа — в этом весь смысл «скелета».

## Как читать тикет

- **Трек** — кто владелец (E1–E5, роли из плана). Один тикет — один автор.
- **Зачем** — что и почему; чтобы студент понимал место фичи в целом.
- **Сустав** — интерфейс, который фича **предоставляет** другим, и что она
  **потребляет**. Это граница ответственности.
- **Готово, когда** — чек-лист приёмки. Пока не все галочки — тикет открыт.
- **Как проверить** — конкретная команда или тест, дающий зелёный/красный.
- **Оценка** — в студенто-днях (≈ полскорости сеньора; парой — быстрее).
- **★ сложность** — 1 лёгкая … 3 требует головы.

## Три правила недели (повесить на видное место)

1. **Сначала контракт, потом реализация.** Заголовок с интерфейсом и тест
   пишутся раньше тела. Тело можно переписать — интерфейс менять только
   добавлением (append-only).
2. **Кость сдаётся с тестом.** «Работает у меня» не считается; считается
   «зелёный ctest / скриншот в CI».
3. **Не трогай чужую кость.** Нужна правка в чужом модуле — заводи запрос к
   владельцу, не правь молча.

## День 0 — онбординг (вся команда, до старта тикетов)

- [ ] Репозиторий клонируется, `cmake -S . -B build -G Ninja && cmake --build build` проходит на пустом скелете.
- [ ] Каждый может запустить `ctest --test-dir build` и увидеть хотя бы один зелёный тест.
- [ ] Полдня — общий созвон: зафиксировать контракты модулей (имена интерфейсов, кто чей владелец). Итог — этот документ + `docs/skeleton.html`.
- [ ] Договориться: ветка на фичу, PR с обязательным зелёным CI, один ревьюер.

## Трек E1 — Ядро и данные

### E1-1 · Математика и хэндлы `★☆☆` · 1 день
**Зачем.** Всё в движке стоит на `Vec3`/`Quat`/`Transform` и типобезопасных
хэндлах. Без этого нельзя начать никому.
**Сустав.** Предоставляет: `Vec3, Quat, Transform` (операции +, *, поворот
вектора, композиция трансформов), `Handle<Tag>` (типобезопасный id).
Потребляет: ничего — это корень.
**Готово, когда:**
- [ ] `Vec3` с +/−/·скаляр, длиной, нормализацией.
- [ ] `Quat` с умножением и `rotate(q, v)`.
- [ ] `Transform{position, rotation, scale}` и композиция двух трансформов.
- [ ] `Handle<Tag>`: разные теги — несовместимые типы (не перепутать объект с телом).
- [ ] Юнит-тест `core_tests` со всеми операциями.
**Как проверить.** `ctest -R core_tests` зелёный; поворот `(0,0,1)` на 90° вокруг Y даёт `(1,0,0)` с точностью 1e-5.
**Грабли.** Кватернион нормализовать; порядок умножения `a*b` — сначала `b`.

### E1-2 · Логирование и конфиг `★☆☆` · 0.5 дня
**Зачем.** Единый лог с уровнями нужен всем подсистемам; конфиг — точка настройки.
**Сустав.** Предоставляет: `LogLevel` (Trace…Critical), `IConfigService`.
Потребляет: `core` (E1-1).
**Готово, когда:**
- [ ] `LogLevel` как enum; функция лога принимает уровень, категорию, сообщение.
- [ ] `IConfigService` с get/set по ключу (строка/число/bool).
- [ ] Мини-тест на round-trip конфига.
**Как проверить.** `ctest -R core_tests`; значение, записанное в конфиг, читается обратно.

### E1-3 · Мир объектов `★★☆` · 2 дня
**Зачем.** Единственный владелец иерархии сцены и трансформов. Остальные держат только хэндлы.
**Сустав.** Предоставляет три интерфейса: `IObjectFactory` (create/destroy),
`IObjectHierarchyAccess` (setParent/parentOf/childrenOf, get/setLocalTransform,
worldTransform), `IObjectQueryService` (exists, nameOf, findByName).
Потребляет: `core`.
**Готово, когда:**
- [ ] Создание/удаление объекта возвращает/освобождает `ObjectHandle`.
- [ ] `setParent` перевешивает объект, `childrenOf` и `parentOf` согласованы.
- [ ] `worldTransform` = композиция локальных вверх по цепочке родителей.
- [ ] `findByName` и `nameOf` работают.
- [ ] Тест `world_tests`: родитель повёрнут — мировая позиция ребёнка считается верно.
**Как проверить.** `ctest -R world_tests`; ребёнок на `(1,0,0)` под родителем, повёрнутым на 90° вокруг Y, в мире оказывается на `(0,0,-1)`.
**Грабли.** Не хранить мировые трансформы — только локальные, мир вычислять. Удаление объекта с детьми — определить политику (удалять поддерево).

### E1-4 · Мир компонентов (data-driven поля) `★★★` · 2 дня
**Зачем.** Компоненты с полями-`variant` — одна инфраструктура позже кормит
Inspector, undo, сцены и параметры скриптов. Ключевое архитектурное решение.
**Сустав.** Предоставляет: `ComponentWorld` (attach/detach, componentsOf),
`FieldValue = variant<float,int64,bool,string,Vec3>`, `ComponentDescriptor`
(typeId, список полей с именами и типами), setField/field/fields.
Потребляет: `object` (E1-3).
**Готово, когда:**
- [ ] Регистрация типа компонента с описанием полей.
- [ ] `attach(object, typeId)` вешает компонент, `componentsOf` его находит.
- [ ] `setField`/`field` пишут и читают значение любого из 5 типов.
- [ ] `fields(component)` возвращает всю карту полей (нужно для сериализации/undo).
- [ ] Тест: attach, записать поле каждого типа, прочитать обратно.
**Как проверить.** `ctest -R world_tests`; `Vec3`-поле round-trip'ится покомпонентно.
**Грабли.** `std::variant` + `std::visit` для сериализации значений; не хардкодить типы полей в UI — только в дескрипторе.

## Трек E2 — Рендеринг

### E2-1 · Vulkan instance + устройство `★★☆` · 1.5 дня
**Зачем.** Точка входа в GPU. Без неё нет ни кадра, ни верификации.
**Сустав.** Предоставляет: инициализированные `VkInstance`, `VkPhysicalDevice`,
`VkDevice`, графическую очередь. Потребляет: `platform` (для surface позже).
**Готово, когда:**
- [ ] Инстанс создаётся; на CI работает софтверный драйвер (Mesa lavapipe).
- [ ] Выбор физического устройства и графической очереди.
- [ ] Логический девайс и очередь получены.
- [ ] Аккуратная очистка в деструкторе (валидация без утечек).
**Как проверить.** Тест создаёт рендерер и проверяет `ready() == true` на lavapipe.
**Грабли.** На CI нет дискретной GPU — только lavapipe; не требовать конкретных расширений сверх минимума.

### E2-2 · Offscreen-таргет `★★☆` · 1.5 дня
**Зачем.** Рисуем не в окно, а в текстуру — это работает headless и лежит в основе всех скриншот-тестов.
**Сустав.** Предоставляет: color-изображение (RGBA) + depth (D32), render pass, framebuffer. Потребляет: E2-1.
**Готово, когда:**
- [ ] Создаются color- и depth-изображения заданного размера.
- [ ] Render pass с clear и правильными layout-переходами.
- [ ] Framebuffer собран, кадр стартует/завершается без ошибок валидации.
**Как проверить.** Кадр с одним clear-цветом рендерится без валидационных ошибок.

### E2-3 · Пайплайн и треугольник `★★☆` · 1.5 дня
**Зачем.** Первый настоящий draw — доказательство, что пайплайн жив.
**Сустав.** Предоставляет: графический пайплайн (вершинный+фрагментный шейдер) и `draw` треугольника. Потребляет: E2-2.
**Готово, когда:**
- [ ] SPIR-V шейдеры собираются (glslangValidator) и встраиваются в бинарь.
- [ ] Пайплайн создан; треугольник рисуется в offscreen-таргет.
- [ ] Цвет треугольника отличается от фона.
**Как проверить.** См. E2-4 — по PNG видно треугольник.
**Грабли.** Vulkan clip space: Y вниз, depth 0..1. Формат вершин зафиксировать сразу (position+normal+uv).

### E2-4 · Readback в PNG `★☆☆` · 1 день — **фундамент верификации**
**Зачем.** Возможность сохранить кадр в PNG превращает рендер в проверяемый: этим пользуется вся команда весь проект.
**Сустав.** Предоставляет: `readbackFrame()` → пиксели, и запись PNG. Потребляет: E2-3, PNG-энкодер (может быть заглушка на неделе 1).
**Готово, когда:**
- [ ] Color-изображение копируется в host-visible буфер.
- [ ] Пиксели пишутся в PNG-файл.
- [ ] CLI/тест: рендер треугольника → `triangle.png`.
**Как проверить.** Открыть `triangle.png` глазами; пиксель в центре — цвет треугольника, в углу — фон.

## Трек E3 — Редактор (.NET)

### E3-1 · Каркас Avalonia + окно `★☆☆` · 1 день
**Зачем.** Оболочка редактора. Пустое окно — но оно должно собираться dotnet'ом и стартовать.
**Сустав.** Предоставляет: запускаемое Avalonia-приложение (.NET 8). Потребляет: ничего (пока).
**Готово, когда:**
- [ ] `dotnet build` проходит с `0 Error(s)`.
- [ ] `dotnet run` открывает окно с заголовком.
- [ ] Есть headless-режим запуска (для будущих скриншотов).
**Как проверить.** `dotnet build editor/avalonia -c Release` зелёный; окно открывается.
**Грабли.** C#-поломки без CI проходят молча — сразу договориться, что смотрим «0 Error(s)» до запуска.

### E3-2 · Докинг и панели-заглушки `★★☆` · 1.5 дня
**Зачем.** Каркас раскладки редактора: перетаскиваемые вкладки Hierarchy/Scene/Inspector/…
**Сустав.** Предоставляет: докинг-раскладку с именованными пустыми панелями. Потребляет: E3-1.
**Готово, когда:**
- [ ] Подключён Dock.Avalonia; 5–6 панелей-заглушек с заголовками.
- [ ] Вкладки перетаскиваются, отрываются, группируются.
- [ ] Пункт меню «Reset Layout».
**Как проверить.** Запустить, потаскать вкладки; раскладка сбрасывается в исходную.

### E3-3 · hello-bridge (P/Invoke) `★★☆` · 1.5 дня
**Зачем.** Первый вызов нативного движка из .NET — доказательство, что сустав C ABI живой.
**Сустав.** Предоставляет: `EngineInterop` с резолвером .so и вызовом `sky_editor_create`/`destroy`. Потребляет: C ABI-заглушку (координация с E5/E1 — сначала пустая функция + тест).
**Готово, когда:**
- [ ] Кастомный DllImport-резолвер находит `libsky_editor_bridge.so` в build-дереве (или по `SKY_BRIDGE_PATH`).
- [ ] `sky_editor_create()` возвращает не-null указатель, `destroy` не падает.
- [ ] В статус-баре/логе редактора видно «bridge OK».
**Как проверить.** Запустить редактор с собранным мостом; отсутствие моста даёт понятную ошибку, а не тихий краш.
**Грабли.** Путь к .so; на этой неделе движок за ABI может быть пустышкой — важен сам факт сквозного вызова.

## Трек E4 — Рантайм и физика

### E4-1 · Мир физики: тела и гравитация `★★☆` · 1.5 дня
**Зачем.** Основа симуляции: тела, которые падают под гравитацией.
**Сустав.** Предоставляет: `IPhysicsWorld` (createBody, setGravity, шаг симуляции, get/setBodyTransform, get/setBodyVelocity). Потребляет: `core`.
**Готово, когда:**
- [ ] Динамическое тело под гравитацией за 1 с падает на ~4.9 м (g=9.81).
- [ ] Статическое тело не двигается.
- [ ] Скорость и трансформ читаются/пишутся.
**Как проверить.** `ctest -R physics_tests`; численная проверка падения за N шагов.
**Грабли.** Фиксированный шаг интегрирования; не путать динамические и статические тела.

### E4-2 · AABB-коллайдеры и резолв `★★★` · 2 дня
**Зачем.** Простейшие столкновения: коробки не проваливаются друг в друга.
**Сустав.** Предоставляет: box-коллайдер, широкая фаза по AABB, разведение пересечений, `CollisionEvent`. Потребляет: E4-1.
**Готово, когда:**
- [ ] Два пересекающихся AABB расталкиваются по оси наименьшего проникновения.
- [ ] Тело, упавшее на статический пол, останавливается на нём.
- [ ] События столкновения собираются за кадр.
**Как проверить.** `ctest -R physics_tests`; куб, брошенный на пол, замирает на высоте пола ± эпсилон.

### E4-3 · Резолв по heightfield `★★☆` · 1.5 дня
**Зачем.** Тела держатся на террейне-высотной карте.
**Сустав.** Предоставляет: heightfield-коллайдер + билинейная выборка высоты. Потребляет: E4-1.
**Готово, когда:**
- [ ] Билинейная высота по (x,z) в локальной системе поля.
- [ ] Динамическое тело поднимается на поверхность поля, если провалилось ниже.
- [ ] Тест: тело на наклонном поле оказывается на нужной высоте.
**Как проверить.** `ctest -R physics_tests`.

### E4-4 · Контракт physics↔object sync `★★☆` · 1 день
**Зачем.** Явная граница: физика и объектный мир синхронизируются вокруг шага, без скрытого двойного владения. Это ключевой сустав между E4 и E1.
**Сустав.** Предоставляет: `IPhysicsSyncContract`/`ObjectPhysicsSync` (bind/unbind тела с объектом, push трансформа до шага, pull после). Потребляет: E4-1, `object` (E1-3).
**Готово, когда:**
- [ ] `bind(body, object)` связывает пару; `unbind` разрывает.
- [ ] До шага трансформ объекта уходит в тело, после — обратно.
- [ ] Тест: привязанный к падающему телу объект опускается в объектном мире.
**Как проверить.** `ctest -R physics_tests` или `integrity_tests`.
**Грабли.** Синхронизация — явная, в обе стороны, вокруг шага; никто не «владеет» чужим трансформом неявно.

## Трек E5 — Пайплайн и QA

### E5-1 · Каркас модулей CMake `★★☆` · 1 день
**Зачем.** Единый способ добавлять модули; без него команда расползётся по разным сборочным стилям.
**Сустав.** Предоставляет: функцию `sky_add_module(name dir sources...)`, структуру `engine/<module>/{include,src}`, алиасы `sky::<module>`. Потребляет: ничего.
**Готово, когда:**
- [ ] `sky_add_module` создаёт статическую библиотеку с público-include-путями.
- [ ] Position-independent code включён (модули линкуются в .so).
- [ ] Пример-модуль собирается и линкуется.
**Как проверить.** `cmake --build build` собирает скелетные модули.

### E5-2 · CI: сборка C++ + ctest под Xvfb `★★☆` · 1 день
**Зачем.** Регрессии ловятся автоматически с первого дня. Без CI C#-поломки и гонки в тестах проходят молча.
**Сустав.** Предоставляет: GitHub Actions workflow. Потребляет: E5-1.
**Готово, когда:**
- [ ] Установка зависимостей (ninja, libx11, mesa-vulkan/lavapipe, xvfb).
- [ ] `cmake --build` и `xvfb-run ctest` на каждый PR.
- [ ] Красный CI блокирует мёрж.
**Как проверить.** Открыть PR со специально сломанным тестом — CI краснеет.

### E5-3 · CI: сборка редактора + скриншот-артефакт `★★☆` · 1 день
**Зачем.** dotnet-сборка редактора в CI (C#-поломки не молчат) + headless-скриншот плеера как артефакт.
**Сустав.** Предоставляет: шаги CI для .NET и загрузку PNG-артефакта. Потребляет: E5-2, E3-1, E2-4.
**Готово, когда:**
- [ ] `dotnet build` редактора в том же workflow; ошибка C# валит джобу.
- [ ] Headless-запуск с сохранением PNG.
- [ ] PNG прикладывается как artifact к прогону.
**Как проверить.** Скачать артефакт из прошедшего CI-рана и открыть картинку.

### E5-4 · Тест-харнесс `★☆☆` · 0.5 дня
**Зачем.** Общий формат тестов, чтобы все писали одинаково.
**Сустав.** Предоставляет: `sky_test.hpp` с макросом `CHECK(...)` и `summary(name)`. Потребляет: ничего.
**Готово, когда:**
- [ ] `CHECK` фиксирует провал с файлом/строкой, не роняя процесс.
- [ ] `summary` печатает «N checks, M failures» и возвращает код выхода.
- [ ] Все треки используют его в своих тестах.
**Как проверить.** Любой из тестов E1–E4 печатает сводку и корректно краснеет при провале.

## Что можно делать параллельно (карта зависимостей недели)

```
Старт сразу (день 1):   E1-1, E2-1, E3-1, E5-1, E5-4
Открываются после них:
  E1-1 → E1-2, E1-3           E2-1 → E2-2 → E2-3 → E2-4
  E1-3 → E1-4                 E3-1 → E3-2, E3-3
  E5-1 → E5-2 → E5-3          (E4-1 → E4-2, E4-3, E4-4; E4-4 ждёт E1-3)
```
**Ни один трек не блокирует другой на старте** — это и есть проверка, что
скелет разрезан правильно. Единственная межтрековая стыковка недели —
**E4-4 ждёт мир объектов E1-3** и **E3-3 ждёт заглушку C ABI**; обе решаются
правилом «сустав двигает верхний»: E4 и E3 пишут ожидаемый контракт и тест
заранее, нижний реализует под готовый тест.

## Ворота недели 1 (что показываем на демо в пятницу)

- [ ] `cmake --build build && ctest` — всё зелёное в CI.
- [ ] `triangle.png` из рендера E2 лежит артефактом в CI.
- [ ] Редактор открывается, панели таскаются, `sky_editor_create` вызвался из .NET.
- [ ] Физика: тело падает, лежит на полу и на heightfield; привязанный объект синхронизирован.
- [ ] У **каждой** сданной кости есть зелёный тест на её суставе.

Если все галочки стоят — команда готова к неделе 2 (M1 «Первый кадр»):
демо-сцена рендерится в док-панели редактора.
